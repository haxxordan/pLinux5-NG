# 12.70 port starting point

Branch: `fw-12.70`, based on upstream `3a7ea6f6c874773641b21d20f95f5df6f648ac40`.
Target: launch-model PS5 Phat, firmware 12.70. No Linux boot is claimed.

The user and I have verified Byepervisor NPT clear on one 12.70 console:
16 VMCBs, zero rejects, cleanup=0, readable kernel text after resume. A
bounded read and reversible write to the HV cave also worked. These tests do
not establish a second root-mode transfer or a Linux boot. The detailed
logs and diagnostics are in the `fw-12.70` branch of
`haxxordan/ps5-linux-loader`.

## Why this base

NG has the high-firmware resume hook, post-resume takeover structure, and
Linux staging path already. Its implementation is currently centered on
13.20: `source/hv/defeat/hv_defeat_1320.c` and
`source/shellcode/hv_takeover/takeover.c` embed firmware-specific offsets and
physical addresses. These must be derived and checked for 12.70 before any
takeover or boot attempt. The 12.70 capture suggests a VMMCALL case at HV PA
`0x62847175`; this is a candidate, not a patch site approval.
`set_offsets()` currently accepts 13.20 but not 12.70, so the existing ELF
will exit during setup on 12.70. Leave that guard in place until the firmware
offsets and takeover path are validated.

## Offset extractor

The published `tools/pl5-offsets.c` uses `sigtable_1320.h`, including 13.20
text/data sizes and signatures. Its standalone ELF expects the kernel to be
readable already; `make offsets` first runs the current 13.20 resume vector.
Neither build is a validated 12.70 payload. Use the table as an offline
signature source, then write a bounded 12.70 extractor after verifying the
memory ranges. Do not treat a first byte match or a `hint` as a resolved
offset.

The pinned 12.70 text image yields two strong offline MP3 candidates:

- `FUN_MP3_INVOKE` at text+`0xaa0c30`: exact unique 21-byte 13.20 signature;
  sixteen command-ID wrappers tail-jump to it, including IDs 21 and 22.
- `FUN_MP3_INITIALIZE` at text+`0xaa1640`: matching long prologue with a
  changed RIP displacement; writes `1` to the readiness flag that the invoke
  function tests at text+`0x3c12f50`.

Neither candidate has been checked against live 12.70 bytes or called.
Run `python3 tools/fw1270_display_preflight.py /path/to/12.70-ktext.bin`
to repeat this check. The tool requires the pinned image size (`0xd50000`)
and SHA-256 (`9d79abbbb4dec7e077d5c65031b84b38955306d0772a7007c675d6e27a446c61`)
before scanning; the capture itself is not included in this repository.

## Next control-transfer gate

The pinned kernel and HV captures support a narrow handoff inventory:
`hv_mp_startup_call` is at text+`0xc9dfb0`; the four-argument
`smp_rendezvous` wrapper is at text+`0xb8fbc0` and tail-jumps to
text+`0xb8f980`. Its setup, action, and teardown callbacks use indirect calls
with CFI checks. The HV dispatcher at PA `0x62846a00` reads the VMCB EXITCODE
and its `0x81` (VMMCALL) jump-table entry reaches PA `0x62847175`. That case
checks a VMCB state byte at `+0x4cb` before it can enter a command dispatch
using the guest register at `+0x5f8`. The dispatcher checks guest `RAX=0x17`
earlier, but that branch only skips telemetry and rejoins the same EXITCODE
jump table. It does not identify a separate safe VMMCALL handler.

Repeat the byte, target, and capture-hash checks offline with:

```sh
python3 tools/fw1270_handoff_preflight.py /path/to/12.70-ktext.bin \
    /path/to/12.70-hv-code.bin
```

The HV image is the 48-page PA `0x62820000..0x6284ffff` capture, SHA-256
`6b07a3cd4d41c29564c86d5335087de5383c6d24b52a14b53f5369da5c2ad910`.
These are offline identifications, not a safe redirect or return contract.
Before any patch, trace the chosen VMMCALL through the state and command
branches, and prove how a one-shot marker can return to the Sony kernel. Keep
Linux staging out of that first marker test.

### Live read-only check

`diagnostics/fw1270_handoff_live.c` checks twelve selected kernel/HV spans
against the pinned captures. It gates on firmware 12.70 and launch-model SoC,
uses the SDK's current kernel text and direct-map bases, writes a synced USB
log, and makes no target-memory writes or VMMCALLs. Run it only on a boot that
has already completed NPT clear; its kernel-text reads are not a test for
whether NPT clear is safe to attempt.

On the launch-model 12.70 console, the ELF with SHA-256
`18dc2e8bfd4659a2d31434f4fb3c27222593996b8423f3f0ff280c184cee3b53`
reported all twelve matches and returned. The USB log
`PS5-12.70-handoff-live-109-1792002926-824358765.txt` (SHA-256
`d0e42469e402760ced6650c008d0f7fd08b8ef051d2b97e70347a4fe14da7246`)
has twelve ordered `result=0,match=1` records and ends
`end,complete=1,matches=12`. Its current kernel text base was
`0xffffffff9fd10000`, different from the earlier offline dump's base; the
text-relative addresses still matched. Elfldr remained reachable afterward.
This validates those live bytes on one boot. It does not prove a safe patch
site, callback contract, or return from a second root-mode transfer.

### VMMCALL probes on the same NPT-clear boot

The CPL3 probe `diagnostics/fw1270_vmmcall_user_probe.c` issued command
`0x1000` once and received `SIGILL` with code 5 (`ILL_PRVOPC`). A separate
bounded test, `diagnostics/fw1270_vmmcall_marker.c`, staged a 34-byte marker
stub in the verified HV cave, redirected the four-byte VMMCALL table slot,
issued the same CPL3 command once, and restored the slot, cave, and marker
cell. The slot and cave readbacks passed, but the marker stayed zero. Thus a
CPL3 call did not establish a second root-mode entry on this boot. Logs are
`PS5-12.70-vmmcall-user-110-1792003132-177167319.txt` and
`PS5-12.70-vmmcall-marker-111-1792003379-808906232.txt`.

`diagnostics/fw1270_vmmcall_gadget_preflight.c` then checked three live
kernel-text gadgets and their executable page mappings. All three matched:
`pop rdi; ret` at text+`0x2a6784`, `vmmcall; pop rbp; ret` at
text+`0xc9dae9`, and `push rbp; push rdi; ret` at text+`0xd22aa7`. The last
two form a balanced return path around VMMCALL. This is a byte and mapping
check, not proof that the chain can return. Its log is
`PS5-12.70-vmmcall-gadgets-112-1792003625-902244226.txt`.

The existing Byepervisor one-shot `getuid` hook accepted that chain in a
preparation-only run, with exact readback and restoration. A trigger using
command `0x1000` reached `before-getuid`, then the console reported
`Fatal trap 9: general protection fault while in kernel mode` and KP'd.
The pinned HV code explains this result: commands outside `4..32` branch
to PA `0x62847f62`, which injects a general protection fault. This crash
does not identify a failed ROP gadget or a failed VMMCALL intercept. The
failed trigger log is `kernel-vmmcall-trigger-1270.log`; it has no return or
cleanup record. The hook and cave therefore require a fresh boot.

The next bounded call uses command `0x17` (decimal 23). Offline, its nested
table target is PA `0x62847eb9`, which calls the helper at `0x62842090`
with a zero guest-register value; that helper writes guest RAX. The dispatcher
also skips telemetry for command `0x17`. The updated preflight pins those
bytes and table targets. This is an offline candidate only until it returns
through the kernel hook and the console remains responsive.

On the next struck boot, `kernel-vmmcall-prepare-1270.elf` installed, read
back, and restored the command-`0x17` chain (`chain_match=1`, all restores
zero). The subsequent trigger caused a black screen and the console powered
off. Its klogsrv capture contains `KVC1270,1,start` but no later checkpoint
or panic text. We cannot tell from that capture whether hook installation,
the `getuid` dispatch, or the VMMCALL itself caused the shutdown. The logs are
`kernel-vmmcall-prepare-1270-reboot2.log` and
`kernel-vmmcall-trigger-1270-reboot2.log` in the testing workspace. The
instrumented revision 2 probe separates these stages with delayed klog
checkpoints. A later fresh boot completed the one-ELF strike with
`survey_count=16`, `cleanup=0`, and readable kernel text; its USB record is
`PS5-12.70-byepervisor-1270-85-1792009900-356292078.txt`. The home screen
then showed its background without icons, while Control Center, elfldr, FTP,
and klogsrv remained responsive. The captured klog showed ShellUI activity
but no fatal trap or explanation for the missing icons.

The revision 2 trigger installed and read back the chain (`chain_match=1`),
returned from `kh_trigger`, then powered the console off during the hooked
`getuid` call. Its capture, `kernel-vmmcall-trigger-1270-v2-live.log`, ends
after a delayed `before-getuid` checkpoint; there is no return marker or
panic text. This localizes the failure to execution of the custom chain or
its VMMCALL, not hook installation.

On another fresh boot the strike showed kernel text and the home screen
returned normally. The skip-VMMCALL diagnostic installed and read back the
same chain, with its target set to the `pop rbp; ret` continuation after
VMMCALL, and again powered the console off during `getuid`. Its capture is
`kernel-vmmcall-skip-1270-live.log`, ending at `KVC1270,2,before-getuid`.
This shows that a hard shutdown can occur in this probe without issuing
HV command `0x17`.
Offline disassembly shows the hooked syscall target at text+`0x312f20` jumps
to text+`0x3573b0`, which dereferences `0x140(%rdi)` immediately. The custom
chain changes `RDI` to a gadget address, whereas the successful marker-only
chain leaves it intact. Failing to restore the thread pointer before the
original syscall resumes is therefore a strong explanation, not yet a live
confirmed fix. Revision 3 sets the hook's resume `RDI` from the current
thread pointer, which its preflight already cross-checks against the pinned
core's current-thread row. It builds cleanly; no revision 3 ELF has run.
Another fresh boot and strike are required to test the corrected skip path.

## Display gap in the current high-firmware path

`source/main.c` skips legacy `shellcode_kernel` for high firmware. That
legacy code copies the 64 KiB VBIOS to physical `0xC0000` and calls the DP
transmitter and MP3/HDCP setup functions. The high-firmware route instead
stages `source/shellcode/hv/boot_linux.c`, which configures VRAM but does not
perform that display setup. The 13.20 display offsets in `off_1320.c` are
therefore unused by the high-firmware route. This can explain a dark HDMI
screen if Linux starts, though AMDGPU logs are needed to identify the actual
failure stage. We need to validate and perform display setup before leaving
the Sony kernel, then record return values and collect Linux logs headlessly.

## Order of work

1. Preserve the verified 12.70 NPT clear path and establish a deliberate,
   bounded second root-mode entry marker. Do not transfer 13.20 patch addresses.
2. Validate 12.70 VBIOS data and the display function identities on the live
   console. Add the VBIOS copy and DP/MP3 calls to the high-firmware staging
   path at the correct point in the Sony kernel lifetime.
3. Boot Linux with a headless log path. Separate PCI enumeration, AMDGPU
   probe/firmware, DRM connector, and HDMI output results before changing
   monitor modes or GPU code.
